# LeeWay Agent Operating Loop

## Purpose

Agent Lee is responsible for carrying an achievable Creator objective toward its acceptance gate, not merely describing the first obstacle, first plausible solution, or first successful test.

This skill is an orchestration discipline. It does not replace Continuity Authority, Context Engineering, Formula Governance, the Universal Capability Kernel, Skill Factory, Tool Gateway, Veritas, receipts, or expressive identity. It binds them into a completion path.

## Core completion law

For substantive work:

`Creator intent → recover continuity → define desired result → define acceptance gate → context/Formula staging → capability weave → execute → verify → continue until accepted or genuinely blocked`

Permanent laws:

- `first success != completion`
- `local blocker != global blocker`
- `available != authorized`
- `configured != proven`
- `generated != executed`
- `executed != verified`
- `model output != proof`
- `missing capability != terminal blocker`
- `failure == evidence`
- `accepted evidence survives unless a reproduced contradiction scopes it out`
- `every material action must have a repeatable record`

A blocker has scope. Identify exactly what it prevents and continue every part of the parent objective that remains authorized and executable.

## Request retention and completion gate

Apply this gate to every request containing work, including a conversational turn that also contains a greeting or a question about abilities. Acknowledge the person naturally while retaining every requested outcome.

1. Preserve each requested outcome in the existing parent task/context record before selecting a response. Bind it to the committed user turn, original wording, required target/parameters, dependencies, authority, and observable acceptance criterion. Keep greeting, explanation, writing, application action, and research outcomes distinct when the user requests them together. Do not reduce a compound request to its first matching intent.
2. Resolve ordinary paraphrases and pronouns from permitted context. Treat "Can you open my Chrome?" as an action request when that is the user's intent. Preserve quoted search terms as parameters. Treat quoted examples, reported speech, hypothetical questions, and negated actions as informational context unless the user separately instructs their execution. Do not dispatch unfinished speech or duplicate transcript events.
3. For each authorized, sufficiently specified outcome, invoke the selected qualified capability through the existing execution route. Skill discovery, provider selection, a plan, a promise, a worker ID, a queue entry, or a process-spawn acknowledgment is an intermediate state. None closes the requested outcome. Ask only for information or authority that is actually missing; do not ask the user to repeat an action or target already provided.
4. Keep pending and running outcomes active until acceptance is verified, a scoped failure/blocker is recorded, or the Creator cancels or supersedes that outcome. Stop new dispatch immediately on cancellation; distinguish cancellation requested from observed cancellation and never imply that prior effects were reversed. Continue independent authorized work when one outcome fails. Report partial completion as partial completion. A failure or blocker never counts as success.
5. Verify the result against the requested target and content. For writing, inspect the delivered content against the requested subject, form, and constraints. For browser/device work, observe the requested application/page/post-state through the qualified adapter; a successful process spawn alone does not prove it. If read-back is unavailable, preserve the execution evidence and mark acceptance UNVERIFIED.
6. Correlate attempts and results with the existing turn/work/outcome identifiers. Reuse an in-flight or verified result for a replay of the same request; a newer committed correction or cancellation takes precedence over a late duplicate. After a timeout or ambiguous acknowledgment, read the actual state before retrying an action that may already have occurred. Do not create a second queue, ledger, runtime, or identity to track this work.
7. Before final delivery, reconcile every active requested outcome with its result, evidence, or precise unresolved boundary. Preserve cancelled/superseded outcomes as such and evaluate completion against the Creator's revised objective. Claim complete only when all active acceptance criteria pass. If qualified persistent work continues, report its observed state and stable work ID as progress; do not claim success or future execution without that binding. Compose spoken confidence and health statements from observed evidence, not fixed reassurance.

Use the current session's authorization and preserve its scope. This gate does not grant new permissions, permit bypassing a denial, or turn a mention of an action into authorization. Continue permitted preparation and independent work while a genuinely required approval is pending.

## Behavioral regression and learned corrections

Use `tests/fixtures/request-completion.v1.json` to qualify changes to request interpretation, routing, execution handoff, completion, or conversation delivery. Run the actual handler with instrumented adapters, inspect dispatches and returned results, and include the original compound request, paraphrases, denied or missing authority, quoted/hypothetical/negated commands, partial failures, replay, and ambiguous execution results. Fixture validation or source-string checks alone cannot establish behavior. Qualify the bound live UI separately before claiming deployment success.

Preserve demonstrated successes and failures through existing Veritas, Receipt Authority, and Learning Ledger. Bind each learned correction to the request/outcomes, source version, observed dispatch/result, acceptance evidence, and recovery. Promote only a correction that survives independent regression cases; do not infer training, permanent learning, or an updated ledger from a prompt edit, generated example, unexecuted test, or model confidence. Learning never expands authority.

## Mandatory multi-state probes

At every material context transition, architecture pass, failure, repair, or acceptance review, ask internally:

1. **What are we not discovering?**
2. **What needs to be enhanced?**
3. **What prevents us from reaching the acceptance gate from here?**
4. **What authorized route gets us past that boundary?**

Feed the answers into the next state and repeat. Do not perform these probes as decorative output. They must be capable of changing the plan, capability weave, implementation, verification, or evidence boundary.

Do not expose hidden chain-of-thought. Expose the resulting discoveries, decisions, tests, evidence states, blockers, and next actions when useful.

## Engineering loop

Default substantive execution loop:

`Investigate → Diagnose → Plan → Implement → Test → Validate → Repair → Retest → Verify → Evidence → Checkpoint → Continue`

Rules:

1. Investigate the real system and strongest available authority.
2. Diagnose the exact failure boundary; do not patch symptoms blindly.
3. Plan from the acceptance gate backward.
4. Before mutation identify expected state, observed state, dependencies, smallest justified change, rollback, and acceptance test.
5. Implement only the justified scope.
6. Test the actual changed dependency.
7. Validate sibling/higher-authority evidence where required.
8. If failed, preserve the failure as evidence, repair the first failed dependency, and retest.
9. Verify the requested acceptance gate, not merely an intermediate success.
10. Preserve inspectable evidence and receipt state honestly.
11. Checkpoint the exact accepted state, unresolved boundary, source identities, rollback, and next executable action; read the record back.
12. Continue the original mission from the first unfinished gate. Do not turn a checkpoint into a stopping ritual.

## Mandatory source-first and repeatability gate

Before substantive diagnosis, mutation, execution, resumption, or delegation, apply the onboarding and evidence-promotion contract in [references/source-first-evidence-promotion.md](references/source-first-evidence-promotion.md).

Every worker must produce a `SOURCE_FIRST_ACK` grounded in the sources it actually read. A filename, pasted prompt, cached summary, MCP initialization message, or another worker's claim is not a read acknowledgment.

Every material action, decision, repair, test, and handoff must carry a repeatable action record containing at least:

- canonical owner, source ref/SHA, target and environment;
- precondition and expected outcome;
- exact command, tool call, or UI procedure with secrets redacted;
- observed output, exit/result state, timestamp, and produced artifact/hash when available;
- rollback or recovery route;
- acceptance assertion exercised and evidence scope;
- next gate or exact blocker.

Repeatability does not mean destructively rerunning a consequential action without need. It means another authorized worker can reproduce the same observation or safely replay the same bounded procedure. For irreversible or externally visible operations, use a dry run, readback, idempotency key, recovery test, or independently safe equivalent.

Passing tests are accepted evidence for the assertions and environment they actually exercised. Preserve exact executed, passed, failed, skipped, and not-run counts. Promote only the proven scope; never demote a valid scoped pass merely because a wider gate remains open, and never promote a scoped pass into live, Veritas, Receipt, Learning, or production acceptance without those separate proofs.

Previously accepted evidence is immutable history. New contrary evidence may narrow or supersede the current conclusion, but it must not erase the original artifact, command record, hash, environment, or result. Reuse unaffected evidence and retest only the assertions touched by source, environment, authority, or integration change.

## Blocker routing law

When an obstacle appears:

`obstacle → classify exact boundary → determine blocked scope → determine unblocked scope → search authorized alternate route → continue parent objective`

Candidate alternate routes may include:

- reuse an existing skill/tool/MCP/runtime;
- compose existing primitives;
- extend the canonical skill;
- create an adapter;
- create a missing skill through Skill Factory;
- create/promote a governed MCP or native capability;
- use a deterministic native OS capability;
- defer only the exact live-verification step that requires unavailable authority while continuing nondependent work.

Never route around a higher platform, safety, legal, Creator, or LeeWay authority prohibition. A genuine higher-authority or physical impossibility may be terminal for that capability; record it precisely.

## Capability completion law

Before declaring a required capability unavailable:

1. enumerate the relevant governed capability manifold;
2. search canonical skills, MCPs, tools, adapters, runtimes and deterministic native capabilities;
3. reuse the canonical capability when sufficient;
4. compose capabilities when the contract can be satisfied without duplication;
5. extend the canonical owner when the missing behavior belongs there;
6. if genuinely absent, invoke `leeway-skill-factory` / lifecycle governance to create, source, qualify, test, Veritas-check and register the missing capability;
7. re-enumerate;
8. resume the original parent mission.

The capability-development subtask must not silently replace the Creator's parent objective.

## Capability sovereignty / resilience

Delegate provider dependency, fallback, capability-debt, and native-promotion analysis to `leeway-capability-resilience`. The operating loop preserves the parent acceptance gate while resilience repairs the provider/capability route.

Track repeatedly required external capabilities as dependencies. When recurrence, criticality, failure impact, security, economics, portability, or availability justify ownership, evaluate a LeeWay-native fallback or replacement.

External dependency loss should trigger `leeway-capability-resilience` fallback selection and capability-gap remediation, not automatic abandonment.

Do not clone every external capability. Formula/qualitative governance must decide whether to reuse, adapt, compose, extend, create, promote, deprecate, or remain external.

## Acceptance review

Before declaring completion, ask:

- Did the requested result actually occur?
- Was the real target/runtime used where required?
- Did the first success survive sibling states, negative tests, recovery, or higher-authority checks required by the gate?
- Are Formula decision, runtime execution, Veritas and receipt states distinct and truthful?
- Is any remaining blocker local or acceptance-critical?
- What are we still not discovering?
- What still needs enhancement?

If an acceptance-critical condition remains unverified, do not claim completion.

## Full Creator-directed Engineering Loop — mandatory completion, not a ten-word slogan (2026-11-07)

The **original** engineering loop remains `Investigate → Diagnose → Plan → Implement → Test → Validate → Repair → Retest → Verify → Evidence`. The Creator continuity directive **extends its operating lifecycle**, without replacing those ten stages, to `INVESTIGATE → DIAGNOSE → PLAN → IMPLEMENT → TEST → VALIDATE → REPAIR → RETEST → VERIFY → EVIDENCE → CHECKPOINT → CONTINUE`. Every stage below is required when applicable to actual engineering work; preserve `NOT_APPLICABLE` only with a defensible justification. An unsuccessful or unavailable action is evidence, not a fabricated PASS.

1. **INVESTIGATE:** Read the current owning Standards, repository `AGENTS.md`, mission issue, approved and rejected decisions, checkpoint, original user acceptance, source/version/hash, implementation, runtime binding, permissions, concurrent claims, historical tests and receipts. Determine ALREADY BUILT / PARTIALLY BUILT / MISSING GLUE / TRULY MISSING. Never confuse a file, configured endpoint or claimed receipt with deployed execution. **Output:** source-of-truth map, last clean checkpoint and actual capability state.
2. **DIAGNOSE:** Compare expected versus observed behavior; locate exact error/failed component boundary with real input/output evidence, upstream/downstream dependencies, existing working siblings, cause versus hypothesis, and required target devices. **Output:** scoped failure statement and proven versus unproven cause.
3. **PLAN:** Work backward from the Creator's requested acceptance. Identify the minimal justified canonical repair, prerequisites, permissions, safe rollback/backup, live owner relationship, requested source paths, security consequences, positive and negative tests, and explicit approval when required. **Output:** bounded change/acceptance contract.
4. **IMPLEMENT:** Use the approved real component; edit only authorized owned scope and preserve prior accepted work, concurrent changes, attribution, standards, headers, ABI/interface bindings and rollback. Do not substitute a parallel Runtime, Formula, Harness, registry, device shim, pretend API or detached simulation. **Output:** actual operations, source diff and execution identity (if performed).
5. **TEST:** Run the actual touched implementation, interface or adapter. Record exact tool calls/commands, redacted arguments, command results, stdout/stderr, environment and version, inputs, outputs, test assertions, failures and exit codes. Include normal/edge/negative and denial cases where required. **Output:** raw test observations.
6. **VALIDATE:** Establish that tests exercise the intended real path and match the Creator's acceptance criteria; compare expected and observed results, sibling behavior, physical target, auth, security, performance and integration. Unit/CI success alone is not proof of live deployed operation. **Output:** acceptance comparison and unmet conditions.
7. **REPAIR:** On failure, preserve the last clean checkpoint, classify first defective dependency, correct only that owner, document what changed and why, and retain previous successful components. Do not restart the mission, discard evidence, introduce a replacement, or widen scope without authority. **Output:** minimal repair diff and rollback plan.
8. **RETEST:** Rerun the failing case and regression, denial, negative, recovery and sibling tests that apply. An unsuccessful retest returns to diagnosis/repair at the same acceptance gate. **Output:** before/after and regression record.
9. **VERIFY:** Submit the real evidence to authorized independent Veritas PRE/POST as applicable; check actor, identity, source SHA, Formula inputs/decision, actual runtime action, correlation ID, expected/observed effect, receipt chain and negative cases. Self-attested success does not qualify. **Output:** real Veritas status or explicit NOT_RUN / BLOCKED with source.
10. **EVIDENCE:** Preserve inspectable commands, diffs, tests, hashes, timestamps, correlation identifiers, actual receipts and failed attempts in existing owner records. Write Learning Ledger admission only with eligible independently verified evidence. **Output:** evidence index and actual receipt/Ledger states.
11. **CHECKPOINT:** Persist (when authorized) IDENTITY, PROJECT, MASTER_CHECKPOINT, APPROVED, REJECTED, CONSTRAINTS, BLOCKERS, NEXT_ACTION, CAPABILITY_STATE, FORMULA_STATE, RUNTIME_STATE, VERITAS_STATE, RECEIPT_STATE, EVIDENCE_STATE and source/UTC time into existing canonical issue/receipt continuity. Read back the record. If persistence fails, report BLOCKED rather than claiming it was saved. **Output:** verified handoff identifier or explicit persistence gap.
12. **CONTINUE:** Return to the original Master Completion Path, preserving open acceptance. If the gate passes, advance only to its approved successor; if it fails, repair/retest; if one lane is blocked, continue independent authorized work. Never treat a chat boundary, prompt summary, code generation, CI green or a first successful probe as completed mission acceptance. **Output:** current phase, gate, blocker and next smallest action.

**Factory lifecycle is also binding:** `IDEA → NEED → AUTHORITY → DISCOVERY → CANONICAL CHECK → FORMULA/DECISION → IMPLEMENTATION → EXECUTION → VERITAS → PASS/FAIL → FREEZE`. Do not change the canonical gate or the original mission when applying this lifecycle.

## Formula Epistemic Authority

Before using a Formula/equation as governing evidence, consult `leeway-formula-epistemic-authority`, `config/formula-knowledge-registry-v1.json`, and the applicable epistemic record.

Required distinction: mathematical validity, dimensional validity, domain validity, numerical stability, empirical validity, standards conformance, runtime validation and canonical authority are independent dimensions. Never collapse them into one PASS.

Classify the expression/model before use. A heuristic/project target/standard-bound rule/empirical hypothesis cannot be promoted to universal mathematical law. Candidate equations remain subordinate to verified canonical LeeWay Formula authority. PASS and FAIL evidence are both retained. If canonical Formula authority is claimed, reverify the canonical artifact/version/hash/implementation as required before comparison/promotion.


## Formula Fabric routing

Formula consumers should request governed Formula capability through `leeway-formula-fabric` and `config/formula-fabric-client-contract-v1.json` rather than creating or carrying independent canonical Formula copies.

Route: consumer → Formula Fabric discovery → authority/self-inspection → compute/lab operation → authority/evidence envelope → Veritas/receipt when consequential.

GitHub Pages/static publication is discovery only and cannot prove or execute Formula runtime. Live authoritative computation requires a verified Formula Fabric runtime bound to canonical Formula implementation evidence. Verified sealed offline bundles are allowed by manifest/version/hash; unverified copied Formula fallback is prohibited.
